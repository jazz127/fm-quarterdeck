# Mobile notifications

Quarterdeck's first Web Push version is an optional, single-owner feature for the existing trusted private HTTPS host. The installation-local Captain's Call alert preference defaults to on; the operator configuration still ships disabled. This document does not authorize production configuration, key creation, service activation, enrollment or physical-device acceptance. Those remain operator actions. No listener, public access, Firstmate hook, daemon or extra notification broker is added.

The supported target is installed iOS/iPadOS Home Screen apps (16.4+) and Android Chrome. Other browsers are feature-detected without a mobile acceptance claim. Preferences contains an installation-local Captain's Call alert checkbox, Enable notifications, Check status and Disable notifications. The boolean lives alongside this installation's existing ID in browser storage: a missing preference defaults to on and an explicit false stays off across refresh/reload. No shared preference, subscription ledger or operator setting is migrated. A preference is not permission, enrollment, a subscription or evidence of delivery. Checking the box only saves the preference; Enable notifications remains a separate deliberate tap. Clearing the box or choosing Disable notifications saves explicit off and uses the existing server-first cancellation and browser cleanup workflow. If that workflow fails, the UI reports incomplete opt-out; a saved local false alone cannot cancel an existing server enrollment. Status separately shows preference, browser permission and configuration/enrollment facts, including operator-disabled, unknown permission and granted permission without enrollment. Only an explicit Enable tap can request OS/browser permission, register the worker and enroll. Granted permission alone does not establish server enrollment. Dismissal can leave permission at default; denial requires a browser/OS settings change. Check status and foreground return reconcile permission and enrollment without prompting or reenrolling. iOS ordinary Safari tabs show an installation hint. Browser storage must be available to preserve this installation's ID. Clearing it can require operator repair rather than duplicate enrollment.

The worker has push and notificationclick handlers only. It never fetches private call details, handles dashboard fetches or caches data. Every push shows fixed text: **Quarterdeck — A new Captain’s Call needs your attention**. The payload has only that text, an opaque event ID and `/#overview`; the worker ignores supplied text and destinations. Click opens or focuses the fixed same-origin Overview and never answers a call. A gone call is handled by the current Overview, not an old notification action.

## Operator configuration and state

On a separately authorized stable Main host, set `FM_QUARTERDECK_PUSH_ENABLED=1` and `FM_QUARTERDECK_PUSH_ORIGIN` to one exact canonical HTTPS DNS origin, without a port, path, userinfo or trailing slash. Select the existing explicit `FM_QUARTERDECK_STATE_PATH` owner (legacy variable compatibility remains). Its normalized, nonsymlink directory must be outside `FM_HOME`, owned by the server user and private (0700). Preserve that owner. UAT, development mode and preview child processes refuse notification configuration. Preview pages cannot enroll the Main owner. Source revision checks still apply to API requests and independently to background sending.

Provide existing operator-owned VAPID material in `quarterdeck-push-keys.json` beside the configured state owner, owned by the server user with mode 0600. The exact JSON fields are `subject`, `publicKey`, `privateKey`; `subject` is a provider-visible `mailto:` contact, and keys use canonical Web Push base64url encoding. The server validates existing material through the maintained, pinned `web-push` library. It never creates or rotates keys. Changing the origin, selected home or public key changes the binding and requires deliberate operator repair; it cannot quietly reset the ledger.

On explicit first enrollment, the existing pending-submission and procrastination owners establish empty evidence files only if missing, preserving existing valid files and refusing corruption. After notification initialization, missing evidence is unavailable and is never recreated by reenrollment. Fresh receipt failure, missing/corrupt pending or parked state, and unavailable/stale calls postpone both baseline and sending.

Private `quarterdeck-notifications.json` contains versioned subscriptions, baseline flags, hashed producer/task identities, immutable event provenance and per-installation outbox results. `quarterdeck-notifications.owner` distinguishes an uninitialized feature from a lost established ledger. Preserve both plus the VAPID file across upgrades and restarts. No subscription/key material lives inside `FM_HOME`, source, HTTP status, logs or the worker. Atomic 0600 files are fsynced with the parent directory. Updates take an exclusive cross-process lock; an abandoned lock or corrupt/lost owner visibly requires operator repair, never automatic deletion/reset. Never delete a live lock. Disabling removes background demand when the last enrollment is off, cancels unsent work, unsubscribes the browser and unregisters this worker; OS permission may remain granted. Accepted vendor messages may still appear. A missing/disabled operator configuration or unreachable private server cannot acknowledge durable opt-out: the UI reports failure and requires configuration/network repair; browser/OS settings remain available to block display.

Capacity is bounded to eight remembered installations, 10,000 seen identities, 10,000 events, 80,000 delivery records and 8 MiB. Disable/revocation removes saved delivery capabilities while installation tombstones and seen identities are retained; reaching capacity fails closed visibly and requires an operator retention decision. Nothing silently prunes identity history and reenrolls old calls.

## Eligibility and delivery

An internal subscriber retains demand on the existing composed call source while enrolled, including when no page is open. It uses the same coalesced snapshot scheduler and per-item receipt adapter. It adds no source parser or independent watcher/daemon. Source cadence, snapshot execution, expiry and provider/device conditions make arrival best effort.

A fresh initial baseline marks existing filed calls without a historical flood. Each installation enrollment waits for a fresh baseline; a new device does not replay events allocated for other devices. A newly observed actionable filed decision or merge allocates one event per selected-home installation binding, producer owner and underlying task, with detectedAt and the source clock (which may be unknown). Detection is not original creation time. Card revisions, summary changes, merge/decision replacement (aliases are retained), rehold, reply, refresh, reenrollment and restart never allocate a second event for that identity. Chat-only asks and missing producer/task identity are excluded. Fresh inputs can still have incomplete source coverage, so hidden calls can be missed.

Expanded per-item answer receipts, pending server submissions and live procrastination suppress newly observed calls and cancel queued work. Replies do not make answered tasks new. Positive local closed-hold evidence can cancel work; omitted/absent cards alone never establish resolution or a new episode and postpone any existing work to expiry. Tab-local unsent drafts/queues are not server evidence and do not provide cross-device suppression. Receipt availability and read time are explicit; the sender deliberately refreshes them immediately before claiming a send, and again after DNS resolution before the real transport. Unknown evidence postpones emission.

The application offers only guarded POST JSON `/api/notifications/status`, `/enroll`, `/disable` operations, with exact schemas, a 4 KiB request ceiling, thirty requests per minute and the state capacities above. Host and Origin must match the operator's exact origin; forwarding headers are not authority. Status returns public VAPID configuration and aggregate provider acceptance, never subscription endpoints or encryption secrets. There is no arbitrary notification text, destination, provider URL or send/test API. The no-auth trusted single-owner environment remains the security model; same-origin checks do not add authentication or tenant isolation.

Destinations are confined to supported HTTPS Apple `push.apple.com` / one-label subdomains and Google `fcm.googleapis.com` Web Push paths, without query, fragment, credentials or custom port. Public IPv4 DNS results are checked and pinned to the TLS connection, with the original vendor hostname's certificate validation. IPv6-only destinations are conservatively refused. Transport uses RFC encryption/signing from `web-push`, no custom cryptography, proxy or redirect following, bounded DNS/network waits and a 4 KiB response bound. Raw provider bodies/errors are withheld.

Events expire fifteen minutes after detection. Ordinary urgency and a stable opaque Topic/notification tag accompany the frozen payload. At most five claimed attempts use bounded exponential delay with jitter and honor Retry-After; a durable ninety-second in-flight lease prevents concurrent restart retries during the bounded transport. A saved ambiguous send retries the same event after its lease, never a new event. 404/410 disables that enrollment and cancels its other unsent work. Other permanent responses stop retrying.

**Provider accepted** means only a successful provider response, never device delivery, display, sound or reading. Timeouts can be acceptance-ambiguous; retries are at least once, and Topic/tag cannot guarantee exactly-once sound. An answer/revision/disable can race a request already in flight or accepted by a provider. Accepted messages cannot reliably be retracted. Offline expiry, Focus, OS settings, browser force-stop and server downtime can suppress/delay arrival. Private network access is required for enrollment, opening and answering; a self-contained alert can arrive while private access is disconnected if internet/vendor delivery remains available.

## Validation boundary

Deterministic tests use neutral synthetic contracts with mocked provider, permission, browser storage and device boundaries. They exercise durable baseline/dedupe/restart/repair/capacity, fresh suppression, retry/expiry/revocation, safe worker payload/click and HTTP origin/state/privacy behavior. Scoped headless desktop/phone evidence establishes UI behavior only. Physical iOS/Android installation, locked/closed/force-stop behavior, private-network-off delivery and actual display/read timing remain separately authorized acceptance; software tests do not prove OS push.
