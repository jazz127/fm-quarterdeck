# First-run pairing: Quarterdeck + Firstmate

A clone is not an installed Firstmate pairing. First install and initialize [kunchenguid/firstmate](https://github.com/kunchenguid/firstmate#quick-start) using its upstream instructions; Quarterdeck does not install or bootstrap the orchestrator. Quarterdeck's existing startup uses the operator's `FM_HOME`; its Preferences view reads that home's single `data/captain.md` record. There is no package installer or alternate preference ledger. Use the explicit terminal onboarding command once before first launch (or to reconcile a later preference version). Neither normal startup, the HTTP API nor `/fm-quartermaster` writes preferences.

## One onboarding contract

1. **Choose skill discovery from a stable approved checkout.** The canonical base set is `skills/fm-lanes`, `skills/fm-toolcheck`, and `skills/fm-quartermaster`. Follow the [integration inventory's per-skill discovery/projection, pinning, rollback and removal gates](FIRSTMATE-INTEGRATIONS.md#manual-activation-and-rollback), including any legacy-skill comparison. Do not project a disposable worktree, overwrite a projection, or assume cloning activates skills. The onboarding preview lists this same set and the discovery instructions; it does not change global projections or install anything. Validate discovery in your Firstmate harness separately.
2. **Select the authoritative Firstmate home and preview the defaults.** From the approved checkout:

   ```bash
   cd prototype
   npm run onboard -- --home /absolute/path/to/firstmate --preview
   ```

   This performs no writes and prints only the proposed owned block, never existing user preferences. Alternatively, omit `--home` in an interactive terminal to be asked for the path. There is no guessed/default home. A configured `FM_HOME` must match the selection exactly; to intentionally migrate to another home, unset that environment variable yourself before selecting the new one. The command refuses the mismatch *before inspecting the other home*.
3. **Confirm before writing.** Stop all other editors/writers of `captain.md`; rerun without `--preview`:

   ```bash
   npm run onboard -- --home /absolute/path/to/firstmate
   ```

   Review the target, action and block, then type the exact displayed `seed <selected absolute home>` confirmation. This confirms both the authority binding and exclusive writer access for this operation. A wrong answer cancels without writing. There is no unattended `--yes`, and applying requires an interactive terminal. Preferences are optional defaults subordinate to user text and explicit task/role authority; conflicts require asking, not silently overriding.
4. **Launch using that same authority.** Onboarding prints a shell-quoted `FM_HOME='…' npm start` command for the existing product startup from `prototype/`. Run it yourself; onboarding never starts/restarts a service. Source belongs at `FM_HOME/projects/fm-quarterdeck`; consult [private owners](PRIVATE-RUNTIME.md) for the existing explicit outside-home taxonomy-state override required with that layout. Keep that `FM_HOME` in your normal launch environment for later starts. No second saved home configuration is introduced. The Preferences view will show the owned base entry alongside existing sections on refresh; it remains read-only.

This terminal-only path requires Node 18+ and Linux with `/proc/self/fd` available, to pin the target directory during publication/cleanup. The live home's `data/`, `state/`, and regular `data/projects.md` must already exist; onboarding does not bootstrap Firstmate itself, search home namespaces, read project content, or run home executables. It refuses relative/root/unnormalized paths, symlinks anywhere in the selected path or required sources, hard-linked files, nonregular records, invalid UTF-8/NULs and oversized preference records.

## Ownership, repeat runs and migration

The exact, versioned block has this boundary (digest and contents are generated by the command):

```text
<!-- fm-agentos-preferences:begin v2 sha256=<digest of known template> -->
…Quarterdeck-owned preference material…
<!-- fm-agentos-preferences:end -->
```

Only recognized, byte-intact templates in `prototype/onboarding.js`'s `OWNED_VERSIONS` catalog can be updated or removed. Matching markers or a newly computed checksum alone do not establish ownership. Duplicate, incomplete, altered, unknown-version or otherwise ambiguous markers are refused, not repaired. The current Quarterdeck template is v2. Exact shipped v1 bytes remain in `prototype/onboarding-legacy.js` for guarded upgrades/removal; markers and locking names deliberately retain their historical namespace. Future releases must retain previously shipped templates and change `CURRENT_VERSION` with a reviewed new template. See [rename compatibility](QUARTERDECK-RENAME.md).

Seeding creates a missing `captain.md` with private permissions, or appends the owned block to an existing file without changing any outside bytes (including BOM, CRLF and missing final newline). Upgrades replace only the intact recognized block and preserve prefix/suffix and ordinary file permissions. Repeat seeding is a no-op without replacing the inode. No skill text, secrets, machine paths, project strategy or standing consequential-action authority is seeded.

The concise defaults cover lane formatting, deliberate read-only tool audits and deliberate Quartermaster checkpoints: recurring failures, regressions, changed assumptions, expanding machinery, evidence-neutral retries and material resource exposure. Quartermaster cohorts can include related labeled and unlabeled work across lanes/epics; labels and individual workers are not automatic causal boundaries. It remains one-shot and advisory, never a daemon, hook, scheduler, continuous review or implementation authority.

An exclusive `.agentos-preferences.lock` serializes onboarding writers. File/path snapshots are checked again after confirmation, after lock acquisition and immediately before atomic publication. Missing-file creation is no-clobber. Changed files/parents or existing locks refuse the operation; temporary names and cleanup are pinned to the inspected directory so a path swap cannot redirect them into another home. This is a local, exclusive-access operator operation, **not a locking protocol for arbitrary editors or a defense against a hostile same-user process**. Do not run it while another writer is active. If a crash leaves a lock, inspect/reconcile the home and establish exclusive access before manually removing only that known lock; the command never breaks locks itself.

## Customize, remove or rebind

Put custom preferences **outside** the markers. Do not edit inside the managed block if you want future automatic upgrades. If it was edited, retain a private copy, inspect the changes and manually reconcile ownership/user content before retrying; no force mode exists.

Preview and remove an intact recognized block with the same target/confirmation protections:

```bash
npm run onboard -- --home /absolute/path/to/firstmate --remove --preview
npm run onboard -- --home /absolute/path/to/firstmate --remove
```

Type the displayed `remove <selected absolute home>` confirmation. Removal restores all outside bytes exactly, retains an empty file rather than deleting it, and does not unbind startup or remove skill projections. To opt out permanently, remove the owned block and do not seed again; ordinary startup will not recreate it. Skill removal/rollback is the separate verified-target operator procedure linked above. To move homes, remove from the old home only if desired, explicitly unset/reselect `FM_HOME`, repeat preview/confirmation for the new home, then use the new startup binding; neither home's user preferences are copied.

## Focused validation

```bash
node --test prototype/test/onboarding.test.js
cd prototype && npm test
# from the repository root, for canonical skill executable-interface checks:
node --test test/*.test.mjs
git diff --check
```

Onboarding tests create synthetic homes under `prototype/data/` in the task checkout and remove only those fixtures. They never use an installed home or global skill projections. Upgrade, preservation, refusal, confirmation and Quartermaster content tests are not proof of installed harness discovery; that remains an operator acceptance step.
